# Phase 8H — GSC Sitemap Processing & Indexation Readiness Audit

Phase 8H is an audit phase, not a content or architecture change. Its purpose
is to determine why Google Search Console reported the apex sitemap index
(`https://waterbalancetools.com/sitemap.xml`) as "Success" with "Discovered
pages: 0" (submitted and last read June 29, 2026), and to determine the
status of the historical, separately-listed `https://www.waterbalancetools.com/sitemap.xml`
entry ("Couldn't fetch"). No Spanish content was expanded, no URLs were
changed, no canonical/hreflang strategy was altered, and no sitemap
architecture was redesigned. This document records the evidence; the
Director-facing summary is `reports/phase-8h-status.md`.

## 2. Repository sitemap architecture (Step 1)

- **Sitemap index + child generator (wired into the build):**
  `scripts/generate-sitemaps.js`, invoked from `scripts/run-all-generators.js`
  at two points (line 228, and again at line 304 as the "post-i18n refresh"
  after `generate-spanish-cluster.js` runs). It walks the repository,
  classifies every `.html` file through `scripts/url-policy.js`'s
  `isSitemapEligible()` (the single source of truth — self-canonical only,
  fails closed for unknown directories, strips a leading language segment
  before classifying category), and writes 8 category sitemaps plus a
  `sitemap.xml` index referencing them.
- **Legacy, unwired generator:** `scripts/generate-sitemap.js` (singular)
  still exists and is reachable only via the standalone `npm run sitemap`
  command. It is **not** called anywhere in `run-all-generators.js` — `npm
  run build` never touches it. It was not modified and is out of scope; it
  is flagged here only because its similar filename could otherwise cause
  confusion during a future audit.
- **Hostname source:** `js/url/url-engine.js` line 3:
  `const BASE_URL = 'https://waterbalancetools.com';` — a single hardcoded
  constant, apex, `https`, no trailing slash, no `www`, no
  `process.env` dependency of any kind (confirmed by grep: no
  `SITE_URL` / `NEXT_PUBLIC_SITE_URL` reference exists anywhere in
  `scripts/` or `js/`). Every sitemap `<loc>`, canonical tag, and hreflang
  `href` in the codebase is built through this one function
  (`absoluteUrl()` / `sitemapUrl()` both delegate to it).
- **robots.txt:** a static, manually maintained file (last touched at
  commit `776541f`, near the initial commit — it is not regenerated by the
  build). Content:
  ```
  User-agent: *
  Allow: /

  Sitemap: https://waterbalancetools.com/sitemap.xml
  ```
  No `Disallow` directives exist at all — nothing is blocked, including
  `/es/`, `/calculators/`, or any child sitemap path.
- **Language-aware inclusion (Phase 8E/8F/8G):** `url-policy.js`'s
  `stripLanguageSegment()` strips a leading `es/` segment (sourced from
  `js/i18n/languages.js`, never a second competing list) before category
  classification, so a Spanish page is treated exactly like its English
  equivalent for sitemap purposes. There is no directory-level skip for
  `es/` in the sitemap generator — eligibility is decided per-file via
  `isSitemapEligible()`, matching the same real-eligibility architecture
  used by navigation/search-index since Phase 8F.
- **Build ordering:** sitemap generation runs **after** all page generators,
  after the Spanish cluster generator, and after hreflang/language-switcher
  injection — so a fresh build's sitemap always reflects the final,
  fully-injected page content, not an intermediate state.
- **Stale-file risk (architectural note, not a defect today):**
  `generate-sitemaps.js` only rewrites a category file if it has ≥1 entries
  (`if (entries.length === 0) continue;`). A category that dropped to zero
  URLs would leave its old file on disk, still referenced by the index.
  This does not currently affect production — all 8 categories have
  entries — but is worth carrying forward as a known characteristic.

## 5. Apex vs www forensic analysis (Step 7)

**This is the single most important finding of the audit.**

`www.waterbalancetools.com` returns `NXDOMAIN` — confirmed independently via
`curl` ("Could not resolve host"), `dig` (empty answer section for both `A`
and `AAAA`), and `nslookup` ("server can't find www.waterbalancetools.com:
NXDOMAIN"). There is no DNS record of any kind for the `www` subdomain — no
`A`, no `AAAA`, no `CNAME`. This is a DNS-zone-level absence, not an
application, redirect, or hosting-config issue, and it cannot be fixed by
any change to this repository.

- The historical GSC entry `https://www.waterbalancetools.com/sitemap.xml`
  → "Couldn't fetch" is **fully explained and expected**: Google could never
  have fetched that URL, because the hostname has never resolved (at least
  not currently, and every generator/content file in this repository was
  already apex-only before this audit — see Section 2).
- Grep across the entire repository (`scripts/`, `js/`, `data/`, plus every
  generated sitemap and every HTML page) found **zero** references to
  `www.waterbalancetools.com` anywhere — not in canonical tags, not in
  hreflang, not in sitemap `<loc>` values, not in robots.txt. Nothing in
  this codebase has ever generated a `www` URL.
- Conclusion: the `www` entry in GSC is an orphaned historical submission
  (most likely a manual one-time GSC submission of a guessed URL, or an
  artifact of an earlier domain-verification step) referencing a hostname
  that is not part of this site's actual architecture. It requires no
  remediation. Google should be — and per the current "Success" entry, is —
  submitting the apex URL.

## 8. Canonical / indexability analysis (Step 5)

`url-policy.js`'s `isSitemapEligible()` — the single source of truth
`generate-sitemaps.js` calls — enforces self-canonical-only inclusion at
generation time: a page whose canonical tag points elsewhere is excluded
from the sitemap outright, and a page with a `noindex` robots meta is
excluded via `isIndexablePage()`. This was true before Phase 8H and is
unchanged. Live spot-checks (Section 7, plus five additional sampled pages
across guides/academy/reference/glossary categories, all `200`) found no
canonical mismatch, no unintended `noindex`, and no unintended redirect on
any sampled sitemap URL.

## 9. Cache / staleness analysis (Step 8)

- Live `sitemap.xml` response headers: `cache-control: public, max-age=7200,
  must-revalidate`, served via Cloudflare edge (`cf-cache-status: HIT` on a
  repeat request with `age: 78`, `cf-cache-status: MISS` on a cache-busted
  query-string request). Both returned byte-identical bodies (verified by
  MD5). A 2-hour edge cache is not long enough to explain a sitemap read
  that is over two months stale relative to GSC's last-read date.
- The live sitemap content matches the currently committed repository state
  exactly (all 9 Spanish URLs present, 487 total URLs, matching
  `validate-url-indexation.js`'s independently-computed count) — production
  is not serving stale or cached-out-of-date content relative to the
  repository.
- **The sitemap-index architecture itself (`generate-sitemaps.js`, the
  `sitemapindex` format currently in production) was introduced in commit
  `1ce7eb6`, dated 2026-06-29 — "Complete Phase 5B.8-5B.9 crawl and indexing
  architecture."** This is the exact same date GSC shows for both
  "Submitted" and "Last read." This is strong circumstantial evidence that
  Google's one and only read of this sitemap happened at or very near the
  moment the current sitemap-index system first went live, and that Google
  has not re-crawled the sitemap in the more than two months since —
  through Phase 7B–7O (SEO/indexing hardening) and Phase 8A–8G (multilingual
  architecture and the Spanish production rollout) — none of which have
  been re-observed by GSC yet.
- A per-file `lastmod` computed from git history for a page committed in the
  *same* commit that also regenerates the sitemap will show a value from
  before that commit exists in `git log` (a one-build lag that self-corrects
  on the next regeneration — confirmed directly: two files newly touched in
  the Phase 8G closeout commit showed a one-day `lastmod` discrepancy
  between the committed sitemap and a fresh regeneration, purely due to this
  git-log timing mechanic). This is cosmetic dating only; it does not affect
  URL presence, count, or validity, and was already self-correcting by the
  time of this audit (Section 11 confirms determinism of the URL set
  itself).

## 10. GSC interpretation (Step 9)

**Classification: 4 — HISTORICAL/STALE GSC STATE WITH CURRENT SITEMAP HEALTHY.**

Direct answer to "is there anything currently wrong with
`https://waterbalancetools.com/sitemap.xml` that would reasonably explain
Google discovering zero pages?" — **No.** Every piece of live production
evidence gathered in this audit (valid XML, valid sitemap-index structure,
8/8 child sitemaps reachable and valid, 487/487 URLs accounted for with zero
duplicates, apex-only hostnames throughout, permissive robots.txt, all 9
Spanish URLs live and correctly tagged, no redirects, no unintended
noindex, healthy short-lived CDN caching) is consistent with a fully
correct, fully crawlable sitemap system today.

What the repository/live evidence **cannot** establish, because it is
outside this repository's visibility, is the internal state of the user's
Google Search Console account: whether Google has attempted and failed a
re-crawl since June 29 for a reason outside this audit's evidence (e.g. a
robots.txt block that existed transiently sometime after June 29 and before
now — not observable retroactively), or how GSC's own UI is currently
displaying per-sitemap discovery counts for an index-type submission. It is
also worth noting for the user's own manual check: Google Search Console's
sitemap report frequently shows "0" (or a blank) discovered-pages figure on
the **index row itself** for a `Sitemap index` type submission, with the
real per-page counts appearing only on the individual child-sitemap rows
nested underneath it once expanded — this is a commonly reported GSC UI
behavior, not something this audit can confirm against this specific
account, and it should be checked directly in the GSC UI as part of any
resubmission (Section 11).

No production defect was found. This is not blind reassurance — it is the
outcome of fetching every live sitemap URL, parsing every one, counting and
cross-checking every URL, and independently confirming DNS state for both
hostnames in play.

  re-read the sitemap and re-evaluate page discovery.

After resubmitting, check in GSC:

1. **Submission status** — should move from "Success" (stale) to a fresh
   "Success" with today's date.
2. **Last read** — should update to the resubmission date, not remain
   June 29, 2026.
3. **Discovered pages** — check both the index row *and* each of the 8
   child sitemap rows individually (Section 10's UI-behavior note); a
   healthy result is each child sitemap showing a non-zero discovered count
   roughly matching Section 3's table.
4. **Child sitemap processing** — confirm all 8 child sitemaps listed
   individually show "Success," not "Couldn't fetch" or "Pending."
5. **Errors/warnings** — confirm none are reported against the sitemap
   itself; page-level indexing decisions (crawled but not indexed, etc.)
   are a separate GSC report from sitemap processing and are out of scope
   for this audit.
